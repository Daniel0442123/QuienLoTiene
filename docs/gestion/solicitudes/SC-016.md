## 2. Descripción

**Qué dice el plan hoy:** producción solo tiene respaldo y restauración (`scripts/respaldo/`). No hay una forma prevista de quitar los datos de prueba.

**Qué se propone cambiar:** agregar `scripts/limpieza/limpiar.sh` con dos modos:
- **pruebas:** borra las cuentas cuyo correo termina en `@prueba.quienlotiene.tech` y todo lo que cuelga de ellas. Sirve antes y después del lanzamiento.
- **total:** borra todas las cuentas de clientes y tiendas. Solo corre si el `.env` tiene `QLT_LIMPIEZA_TOTAL_PERMITIDA=si`, y esa línea se quita al salir a producción real.

En los dos modos el script saca un respaldo antes de borrar, pide escribir el dominio del sitio y anota cada ejecución. Nunca borra las cuentas ADMIN, las categorías, la auditoría ni la estructura.

Además, desde ahora las pruebas que se hagan en producción usan correos `@prueba.quienlotiene.tech`.

**Motivo:** mientras el sitio es un ambiente de producción-pruebas, QA prueba en producción y esos datos no deben quedar cuando entren usuarios reales.

## 3. Análisis de impacto

| Aspecto | Impacto | Detalle |
|---|---|---|
| Alcance | Ninguno | No cambia ninguna historia |
| Cronograma (días) | 0 | |
| Calidad y pruebas (casos que cambian) | Bajo | Ningún caso cambia. Las pruebas en producción usan cuentas `@prueba.quienlotiene.tech` |
| Riesgos nuevos o que cambian | Medio | Un borrado por error en producción. Lo mitigan el respaldo previo obligatorio, la confirmación con el dominio, `--simular` y el bloqueo del modo total |
| Otros integrantes afectados | Bajo | QA: usar cuentas de prueba marcadas. Quien tenga SSH al VPS: ejecutar el script cuando se pida |
| Costo o esfuerzo (horas) | Menos de 3 | |

**Alternativas consideradas:**
- Restaurar un respaldo limpio. Se descarta porque también borraría los cambios reales hechos desde ese respaldo.
- Vaciar las tablas a mano con SQL. Se descarta porque no tiene respaldo previo ni registro, y es fácil olvidar una tabla, ya que los módulos no tienen llaves foráneas entre esquemas.
